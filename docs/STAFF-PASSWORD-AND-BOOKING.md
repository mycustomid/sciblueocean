# Password-only staff access and Miague booking flow

Current policy (2026-10-28), explicitly selected by Bos: individual username/email and password, no authenticator. This supersedes the earlier MFA prototype and managed-IdP proposal for this local runtime.

- Six role accounts exist in the private database: manager, reception, housekeeping, finance, maintenance and owner. Roles come from server records, never a login selector. Strong generated passwords are issued directly to Bos and are not committed or placed in project documentation.
- Passwords use Argon2. Sessions are opaque, hashed in SQLite, HttpOnly and SameSite=Strict, with server idle/absolute expiry and revocation. Cookie Secure is reserved for a reviewed HTTPS deployment; current listener is loopback HTTP.
- Ten cumulative failed verifications permanently ban the source IP (HTTP403, no Retry-After). This is an application-level staff-login ban stored in SQLite; it survives restarts. Account-level throttling remains temporary to mitigate distributed guessing without permanently locking a targeted account. Successes do not count. Failure accounting is serialized and hash concurrency bounded. Source IP comes from the socket, not a client-controlled forwarded header. A local reverse proxy shares its loopback peer; a future internet ingress needs reviewed trusted-proxy source attribution and edge limits.
- CSRF, Origin/Host validation, role checks, property scope, canonical-path protection and guest-data minimization remain enforced. No claim that brute force is the only possible attack or that the site cannot be hacked.
- Guest flow: search dates/party -> Miague -> request details -> pending receipt -> guest sees the explicitly fictional transfer account `1234567890` and a WhatsApp link to `+62 812-9636-1446` -> guest manually sends transfer proof -> reception checks WhatsApp, chooses a free room and confirms in Studio. The request form requires a phone number. No real transfer should be sent to the dummy account. Room assignment is transactionally checked against overlapping confirmed/in-house stays. UUID idempotency avoids duplicate requests on retries. Only Miague can be requested; Ebène/Amara remain interest-only. The separate payment-provider code is retained but not connected to this local test flow.
- The legacy localhost8765 listener now redirects GET pages to8766 and refuses old credential POSTs; the old demo service is stopped. Astro development and the Node local server route Studio/staff/guest APIs to the operational service. Public static templates use operational assets and a username/password form.
- Start with scripts/start-operations.ps1. Primary local entry: http://127.0.0.1:8766/experience/ and /studio/.
- Source changes are not a public Vercel/backend deployment. External notifications and online payment collection remain unconfigured. The local service is not a Windows startup service.

Evidence: QA/operations-password-auth-security.log, QA/operations-browser/fixture-result.json, QA/operations-browser/role-logins.json and QA/operations-password-semgrep.json. Credentials never belong in these evidence files.


Permanent IP ban recovery is local-admin only: `.\.venv-operations\Scripts\python.exe operations-server\app.py unblock-ip --ip 127.0.0.1 --username ACCOUNT`. Replace IP/account as appropriate. This removes the ban and failure counters; it never changes the password. There is no HTTP endpoint for unbanning. Shared/dynamic IPs can affect legitimate users, and switching IPs can evade an IP-only ban. Current loopback proxies share a source address; internet deployment still needs reviewed ingress source attribution.
